## bug_019 — TUN repair re-installs hijacked preflight gateway as system default

**Severity:** normal
**File:** `internal/repair/repair.go:343-348`

### PR Comment

TUN repair re-installs the preflight default-route gateway after deleting the freshly-installed DHCP route. In the canonical Clash/Mihomo TUN-hijack scenario this rescue is designed for, the preflight gateway is the TUN gateway (e.g. `198.18.0.1` via the now-downed `utun0`), so the rescue silently re-hijacks routing or blackholes egress. Fix: skip the explicit route add (the DHCP renewal earlier in the plan already installs the correct default route), or query `route get default` after DHCP completes, or refuse to install a gateway that matches the diagnose TUN signatures (`198.18.0.0/15`, `fdfe:dcba:9876::1`).

### What the bug is

`buildTunActions` in `internal/repair/repair.go:343-348` ends the TUN repair plan with:

```go
if pre.Network.DefaultRoute.Gateway != "" {
    actions = append(actions,
        action{ID: "tun.route.delete.default", ..., Args: []string{"delete", "default"}, IgnoreFailure: true},
        action{ID: "tun.route.add.default",
            Description: "Add default route via DHCP gateway " + pre.Network.DefaultRoute.Gateway,
            ..., Args: []string{"add", "default", pre.Network.DefaultRoute.Gateway}, IgnoreFailure: true},
    )
}
```

The variable name and Description string both call this the *DHCP gateway*, but `pre.Network.DefaultRoute.Gateway` is captured at preflight, **before any rescue action runs**. In the canonical state this rescue is built for (Clash/Mihomo TUN owns the default route), the preflight gateway is the TUN-hijacked gateway, not a LAN gateway.

### Why this fires on the targeted use case

`internal/diagnose/tun.go` explicitly flags `198.18.0.1`, `198.18.0.0/15`, and `fdfe:dcba:9876::1` as Clash/Mihomo TUN signatures, and `classify.RecommendedRepairLevel` returns `"tun"` exactly when `ClashTunActiveOrStale` is set. So the v0.5 orchestrator preferentially routes to `LevelTun` precisely when `pre.Network.DefaultRoute.Gateway` is one of those TUN-side IPs.

### Step-by-step proof (Clash Verge TUN active)

1. Preflight: `route get default` → `gateway 198.18.0.1, interface utun0`. `pre.Network.DefaultRoute.Gateway = "198.18.0.1"`, `pre.Network.DefaultRoute.Interface = "utun0"`. `DiagnoseTun` marks utun0 suspicious; classifier sets `CLASH_TUN_ACTIVE_OR_STALE`; orchestrator picks `LevelTun`.
2. `tun.ifconfig.down.utun0` brings utun0 down.
3. Wi-Fi cycle (`-setairportpower off`, sleep, `on`) and `tun.ipconfig.dhcp.en0` (`ipconfig set en0 DHCP`) cause macOS to install a real LAN default route, e.g. `192.168.1.1 via en0`.
4. `tun.route.delete.default` deletes that *good* LAN default route.
5. `tun.route.add.default 198.18.0.1` tries to install the TUN gateway. With utun0 down and `198.18.0.0/15` unreachable on en0, `route(8)` either rejects with "Network is unreachable" or installs a phantom route pointing at a downed interface. Either way, all egress traffic blackholes.
6. `IgnoreFailure: true` masks the misconfiguration in the action log, so the report does not flag step 5 as a failure.

### Why the safety nets do not catch it

- `criticalWorsened` (lines 580-602) catches `pre.DefaultRoute.Present && !post.DefaultRoute.Present`. If the add succeeded with a phantom route, `Present` stays true and the comparator does not fire. If the add failed and there is now no default route, the comparator does fire and triggers auto-rollback — but rollback only restores quarantined files, not the route table, so the user is left with both the residue quarantines reverted (Clash residue back) **and** a broken default route.
- `IgnoreFailure: true` on the delete+add pair means the `route(8)` failure is silent in the report.
- The existing test `TestTunRepairPlanIsTargeted` plants `Gateway: "192.168.1.1"` (LAN) — it never exercises the canonical TUN-hijack scenario.

### Fix shape

Any one of the following is sufficient and aligns with what the surrounding code already does:

- **Drop the explicit add.** `tun.ipconfig.dhcp.<wifiDevice>` and the Wi-Fi cycle already cause macOS to install the correct default route from DHCP. The delete+add pair is redundant in the happy path and harmful in the targeted scenario.
- **Re-query after DHCP.** Run `route -n get default` after step 3 and only add a default route if the post-DHCP read disagrees, using the post value rather than the preflight value.
- **Refuse known-bad gateways.** Skip the add when `pre.Network.DefaultRoute.Gateway` matches the same TUN signatures `DiagnoseTun` already classifies as suspicious (`198.18.0.0/15`, `fdfe:dcba:9876::1`), or when `pre.Network.DefaultRoute.Interface` starts with `utun`.

Fix the description string at the same time — `"Add default route via DHCP gateway "` is misleading; the value is the preflight gateway, not a DHCP-derived one.

## bug_022 — `guidedCanApply` gate never matches orchestrator dry-run status `"planned"`

**Severity:** normal
**File:** `gui/CactusAgentLinkRescue/Sources/CactusAgentLinkRescue/AppState.swift:200-214` (gate at `:436`)

### PR Comment

The apply-card gate at `AppState.swift:436` still requires `report.status == "dry_run_complete"`, but this PR rewires `runGuidedRescue` to invoke `orchestrator rescue` (`AppState.swift:211`), and the orchestrator's dry-run terminal status is `"planned"` (`orchestrator.go:113`), never `"dry_run_complete"`. As a result, after a successful orchestrator dry-run from `GuidedRescueView`'s Analyze Only button, `guidedCanApply` stays false forever and the in-pane 'Run Guided Repair' apply button never appears. The adjacent `guidedStatusLabel` and `guidedStepStatus` were updated for the new orchestrator statuses (`ticket_created`, `restart_required`, `rolled_back_after_worsening`) but this gate was missed; fix is one line — accept `"planned"` (or rename the orchestrator dry-run status to `dry_run_complete`).

### What the bug is

`AppState.swift` lines 200-214 (`runGuidedRescue`) now invoke `orchestrator rescue` instead of the legacy `guided rescue` subcommand:

```swift
var args = ["orchestrator", "rescue", "--target", rescueTarget == "network" ? "clash-tun" : rescueTarget, "--json"]
```

But `applyGuidedReport` (`AppState.swift:436`) still gates the apply button on the legacy guided-rescue status string:

```swift
guidedCanApply = report.status == "dry_run_complete" && report.mode == "dry-run" && report.selectedRecipe != nil
```

The orchestrator never emits `"dry_run_complete"`. Looking at `internal/orchestrator/orchestrator.go` around line 113:

```go
if dry {
    report.Status = "planned"
    report.HumanSummary = "Targeted Clash/TUN repair dry-run is complete. No changes were made."
    report.NextAction = "agentlink ticket create --type clash-tun-fix --json"
    return finish(report, opts.Home)
}
```

The full set of orchestrator terminal statuses is: `healthy`, `planned`, `repaired`, `manual_action_required`, `ticket_created`, `restart_required`, `rolled_back_after_worsening`, `failed`. None equals `"dry_run_complete"`.

### Step-by-step proof

1. User clicks 'Analyze Only' on `GuidedRescueView`. AppState calls `runGuidedRescue(allowRepair: false)`.
2. `runGuidedRescue` runs `agentlink orchestrator rescue --target auto --dry-run --json` (line 211 with `--dry-run` appended at line 215).
3. Orchestrator returns `{"status":"planned","mode":"dry-run",...}` per `orchestrator.go:113-117`.
4. `applyGuidedReport` runs the gate: `"planned" == "dry_run_complete"` → false, so `guidedCanApply = false`.
5. `GuidedRescueView.swift:16` wraps applyCard in `if state.guidedCanApply || state.executeEnabled`. `executeEnabled` (`AppState.swift:85`) is keyed off the legacy `dryRun` (`RepairReport`) state populated by the brain repair flow, which is *not* populated by orchestrator runs — so it is also false.
6. The applyCard never renders, and the 'Run Guided Repair' button on the apply card is unreachable through the new orchestrator-backed Analyze Only flow.

### Why existing code does not prevent it

The diff did update the *display* helpers for the new statuses — `guidedStatusLabel` got cases for `ticket_created`, `restart_required`, `rolled_back_after_worsening` (`AppState.swift:470-472`), and `guidedStepStatus` got matching warn cases. The label/step machinery handles the orchestrator vocabulary correctly. Only the apply gate at line 436 was left tied to the retired `dry_run_complete` token. There is no migration shim that aliases `planned` to `dry_run_complete`.

### Impact

Functional but degraded: `GuidedRescueView`'s applyCard escalation path is dead code after every orchestrator dry-run. Users still have alternate routes:

- Hero card 'Allow Reversible Repairs' / `StatusDashboardView` 'Fix My Connection' confirmation dialogs both call `runGuidedRescue(allowRepair: true)` directly without going through the apply card.
- The 'Create Terminal Ticket' button on the field-mode landing also bypasses the gate.

So the feature isn't catastrophically broken, but the design intent of 'analyze, review the plan in the apply card, then click Run Guided Repair' is unreachable in v0.5.0.

### Fix

One-line fix at `AppState.swift:436`. Either accept both tokens:

```swift
guidedCanApply = (report.status == "planned" || report.status == "dry_run_complete") && report.mode == "dry-run" && report.selectedRecipe != nil
```

…or rename the orchestrator dry-run status in `orchestrator.go:113` to `dry_run_complete` so existing GUI gates and any other downstream consumers keep working.

**Severity:** normal
**Source bugs:** `bug_023`, `bug_027` (merged)
**File:** `gui/CactusAgentLinkRescue/Sources/CactusAgentLinkRescue/Views/RescueView.swift:39-45` + `internal/repair/repair.go` (buildActions)

### PR Comment

The v0.5.0 standard/standard-system-reset split is incompletely propagated in two places:

1. **RescueView's networkAdvanced disclosure** (`Views/RescueView.swift:39-50`) still only renders Safe/Standard/Deep CommandPreviews and the help text reads 'safe/standard/deep' — users following the Expert Console path get the new lighter Standard with no breadcrumb to `standard-system-reset`, while `GuidedRescueView` was updated to surface both.

### Bug Summary

The v0.5.0 release split the legacy `standard` rescue into two levels: a lighter `standard` (Wi-Fi refresh only) and a new `standard-system-reset` (broad clean-location/route-flush/DHCP-renew). The split was applied to the CLI flag list, `GuidedRescueView`, the field package README, and the `repair.LevelStandardSystemReset` constant, but two places were missed.

`gui/CactusAgentLinkRescue/Sources/CactusAgentLinkRescue/Views/RescueView.swift:39-50` still renders only three CommandPreviews — Safe/Standard/Deep — under the "Network Rescue Advanced" disclosure, with help text `"Network rescue safe/standard/deep may require sudo..."`. There is no `tun` preview and no `standard-system-reset` preview. `GuidedRescueView` in the same PR was updated to show **Targeted Clash/TUN Repair**, **Standard System Reset (fallback)**, and **Deep Repair (final resort)**, so the team clearly knew the new levels needed surfacing — RescueView (the Expert Console path) was just missed.

The `state.sudoRescueCommand(level:)` helper at `AppState.swift:520-527` already handles `tun` and `standard-system-reset` correctly, so the fix is purely to add CommandPreview rows and update the disclosure copy.

### Issue 2: Standard Auto-Escalates Silently

`internal/repair/repair.go` `buildActions()` at lines ~272-286:

```go
if level == LevelStandard {
    if !shouldUseSystemReset(pre) {
        if wifiService := findWiFiService(pre); wifiService != "" {
            actions = append(actions, ... wifi-off/sleep/wifi-on ...)
        }
        return actions
    }
    // implicit fall-through to broad block when shouldUseSystemReset(pre) is true
}
```

`shouldUseSystemReset` at lines 482-491 returns true when `!pre.Network.DefaultRoute.Present` or any of `NoActiveInterface`/`NetworkLocationSuspected`/`SysconfigSuspected` classifications are present. Those conditions describe **exactly the failure modes a user invoking `rescue --level standard` is most likely to be in** (the network is broken, which is why they ran rescue).

The README diff explicitly states: *"`standard` includes safe rescue and a lower-impact Wi-Fi refresh by default. The old broad clean-location/route-flush behavior is demoted to `standard-system-reset`."* The word **demoted** strongly implies a clean separation. The actual behavior is: standard is light unless the code thinks you need more, in which case it silently runs `standard-system-reset` actions without `--yes` confirmation for the broader-impact steps.

### Step-by-Step Proof of the Auto-Escalation

1. User runs `sudo agentlink rescue --level standard --yes` on a Mac with a stuck network location and no default route.
2. Preflight diagnose collects `pre` and Classify adds `NO_DEFAULT_ROUTE` (and possibly `NETWORK_LOCATION_SUSPECTED`).
3. `buildActions(LevelStandard, pre)` is called.
4. After the safe-tier service-loop and DHCP renews are appended, control reaches `if level == LevelStandard {`.
5. `shouldUseSystemReset(pre)` returns `true` because `!pre.Network.DefaultRoute.Present`.
6. The `if !shouldUseSystemReset(pre) { ... return actions }` early-return is skipped.
7. Execution falls through past the `if` block into the `cleanLocation := "AgentLink-Clean-" + ts` block at line ~287.
8. The user gets `networksetup -createlocation`, `-switchtolocation`, route flush x2, all-port `ipconfig set DHCP`, and Wi-Fi cycle — i.e. the full `standard-system-reset` plan.
9. The README told them this behavior was demoted to a separate level requiring explicit opt-in.

### Impact

- **GUI inconsistency:** Expert Console users copy `Standard Rescue` expecting v0.4 behavior; depending on system state they either get a lighter Wi-Fi cycle (surprising in the other direction) or the auto-escalation. There is no in-GUI breadcrumb to `standard-system-reset` in RescueView at all.
- **CLI/docs contract mismatch:** The "demoted" language is misleading whenever the auto-escalation triggers. A test exercising `LevelStandard` with `!DefaultRoute.Present` would observe the broad block being executed despite the level name.
- **Severity rationale:** The auto-escalation arguably matches what a panicked user in v0.4 would expect (Wi-Fi cycle alone won't fix a missing default route), so it's not a hard correctness defect. But the surface-vs-behavior gap is worth fixing before this becomes the new contract.

### Suggested Fix

Pick one, not both:

- **Strict separation:** gate the broad block on `level == LevelStandardSystemReset || level == LevelDeep` only. Make `LevelStandard` always Wi-Fi-only. Update RescueView to expose `Targeted Clash/TUN Repair` and `Standard System Reset` CommandPreviews and rewrite the disclosure copy as `"safe/tun/standard/standard-system-reset/deep"`.
- **Documented auto-escalation:** keep the fall-through but add a sentence to README and the RescueView disclosure: `"standard auto-escalates to standard-system-reset when no default route is present or sysconfig is suspect."` Still add the missing CommandPreview rows in RescueView so users have a breadcrumb to the explicit level.

## bug_014 — Brain server child not detached; SIGHUP from terminal close kills the daemon

**Severity:** normal
**File:** `internal/brain/server.go:75-91`

### PR Comment

`brain.StartServer` launches `llama-server` via `exec.CommandContext` without setting `cmd.SysProcAttr.Setsid` (`internal/brain/server.go:75-91`), so the child inherits the agentlink CLI's process group, session, and controlling terminal. When the user closes the Terminal window that ran `agentlink brain server start`, the kernel sends `SIGHUP` to the controlling tty's session and kills `llama-server`, defeating the documented purpose of leaving a long-running daemon listening on `127.0.0.1:8080` for OpenCode. Fix by setting `cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true}` before `cmd.Start`, and ideally redirecting stdin to `/dev/null` and stdout/stderr to a log file.

### Bug

`brain.StartServer` is the entry point that the docs (`docs/offline/OPENCODE_BRIDGE.md`) and the OpenCode local-Gemma flow (`opencode configure-local-gemma`) tell users to run so that `llama-server` keeps listening on `127.0.0.1:8080` after the CLI returns. The implementation at `internal/brain/server.go:75-91` is:

```go
cmd := exec.CommandContext(ctx, avail.ServerPath, "-m", avail.ModelPath, "--host", "127.0.0.1", "--port", strconv.Itoa(port), "-c", "8192")
cmd.Stdout = nil
cmd.Stderr = nil
if err := cmd.Start(); err != nil { ... }
rep.PID = cmd.Process.Pid
_ = os.WriteFile(rep.PIDFile, []byte(strconv.Itoa(rep.PID)), 0644)
time.Sleep(500 * time.Millisecond)
```

`cmd.SysProcAttr` is never set, so on macOS/darwin `llama-server` inherits the parent agentlink CLI's process group, session, and controlling terminal. Stdin is also left attached to the parent's tty.

### How it manifests

The CLI returns ~500ms after `cmd.Start()`, and `llama-server` is reparented to launchd. So far so good — but reparenting only changes the parent PID; it does not change the session or controlling terminal. `llama-server` is still in the original Terminal window's session.

When the user later closes the Terminal window where they ran `agentlink brain server start` (the documented one-shot pattern in the OpenCode bridge docs), macOS tears down the session: the kernel sends `SIGHUP` to every process whose controlling tty is that pty. `llama-server` receives `SIGHUP` and dies, even though the user (and the documentation) expect it to outlive the CLI invocation.

### Why existing code does not prevent it

1. `exec.CommandContext` does not detach a child by default — `SysProcAttr` is the only knob, and it is left unset.
2. The `ctx` used here is `context.Background()` from `cli/cli.go`, so `exec.CommandContext` itself does not kill the child on CLI exit. (One verifier flagged this as part of the original bug description; that part is benign today, but the SIGHUP/session issue is unrelated and remains.)
3. The 500 ms sleep + listening probe only checks that the socket is up at hand-off; it cannot prevent SIGHUP delivery later.
4. There is no `/dev/null` redirection of stdin/stdout/stderr, so the child also keeps a handle to the controlling terminal even if a future fix only addresses session handling.

### Impact

The single feature this code exists to support — a long-running local OpenAI-compat server on `127.0.0.1:8080` for OpenCode — breaks under the normal user workflow of "run `brain server start`, then close that Terminal window, then use OpenCode". The user has to keep the Terminal window open or relaunch the server, and OpenCode requests will fail with connection-refused once the window is closed.

This is reliability, not catastrophic — the user can re-run `agentlink brain server start` — but the daemon design is wrong for the documented use case.

### Step-by-step proof

1. User runs `agentlink brain server start --port 8080 --json` from Terminal.app.
2. `brain.StartServer` is called. Because `cmd.SysProcAttr` is nil, `os/exec` calls `fork`/`execve` with no `setsid`. The child inherits PGID, SID, and controlling tty from the agentlink CLI process, which inherited them from the user's shell.
3. After `cmd.Start()`, `time.Sleep(500ms)`, and the listen probe, `StartServer` returns. The CLI process exits.
4. `llama-server` is reparented to PID 1 (launchd). It still reports the same SID/PGID and same `/dev/ttysXXX` as the original shell.
5. The user closes the Terminal window. Terminal.app exits, the pty master is closed, and the kernel delivers `SIGHUP` to every process in that session (including `llama-server`, which has not installed a SIGHUP handler that ignores it and is not in its own session).
6. `llama-server` exits. The PID file at `~/Library/Application Support/Cactus AgentLink Rescue/brain-server/llama-server.pid` becomes stale. Subsequent `agentlink brain server status` reports `stopped` and OpenCode requests to `http://127.0.0.1:8080/v1` fail.

### Fix

Detach the child into its own session before `Start`:

```go
cmd := exec.CommandContext(ctx, avail.ServerPath, ...)
cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true}
cmd.Stdin = nil // or os.Open("/dev/null")
// ideally redirect stdout/stderr to a rotated log file under brain-server/
```

`Setsid: true` makes `llama-server` a new session leader with no controlling terminal, so SIGHUP from the original tty's session teardown is no longer delivered to it. Optionally redirecting stdin to `/dev/null` and stdout/stderr to a log file under the same `brain-server/` directory completes the macOS daemonization pattern and makes future debugging easier without holding tty fds.

## bug_026 — Dead self-assigning conditional in orchestrator target normalization

**Severity:** nit
**File:** `internal/orchestrator/orchestrator.go:39-41`

### PR Comment

Lines 39-41 contain a self-assigning no-op: `if target == "clash-tun" { target = "clash-tun" }`. The block has no effect at runtime — `supervise()` already treats `network`, `clash-tun`, and `auto` identically — but it misleads reviewers into thinking some normalization is intended (e.g. `clash-tun` → `network`). Either delete the block or replace it with the actually intended mapping.

### What the bug is

In `internal/orchestrator/orchestrator.go` at lines 39-41, after defaulting empty target to `"auto"`, the code does:

```go
if target == "clash-tun" {
    target = "clash-tun"
}
```

This is a self-assignment guarded by a conditional comparing the variable to its post-assignment value. The body of the `if` is identical to the condition; whether the branch is taken or skipped, `target` is unchanged. The block compiles to a dead store.

### Why it doesn't manifest as a runtime defect

Tracing the downstream consumers of `target` in the same file confirms the no-op hides nothing:

- `supervise()` accepts `target == "network" || target == "clash-tun" || target == "auto"` for the TUN-rescue branch and runs identical logic for all three.
- `report.Target` is only stamped into the JSON output.
- Upstream, `gui/AppState.swift:211` already maps the user-facing `network` to `clash-tun` before invoking the CLI, and `cli.go runOrchestrator` passes `--target` through unchanged.

So by the time control reaches `Run()`, `clash-tun` is already canonical, and the no-op neither rejects unsupported targets nor performs aliasing.

### Why it still matters (clarity bug)

Reading the code, a reviewer sees the empty-string normalization on lines 36-38 (`if target == "" { target = "auto" }`) followed immediately by the clash-tun stanza in the same shape, and reasonably assumes some normalization was *intended* — perhaps `clash-tun` → `network` to match `auto`'s alias semantics, or vice versa. The committed code dropped that intent and left only the scaffolding. Future readers will waste time deciding whether the block is load-bearing.

### Step-by-step proof of the no-op

1. Caller invokes `Run(ctx, runner, Options{Target: "clash-tun", ...})`.
2. Line 35: `target := opts.Target` → `target = "clash-tun"`.
3. Line 36-38: `target != ""`, so the auto branch is skipped.
4. Line 39: `target == "clash-tun"` is true.
5. Line 40: `target = "clash-tun"` writes the same value already held.
6. After line 41: `target == "clash-tun"`, identical to the value before line 39.
7. Removing lines 39-41 produces byte-for-byte identical observable behavior.

### Fix

Either delete the three lines (simplest, behavior-preserving), or implement the actually-intended normalization. If aliasing was intended, a likely candidate is `if target == "network" { target = "clash-tun" }` to make Go-side canonicalization match the GUI mapping — but this is a guess; the author should confirm intent.

## bug_012 — `GemmaUsed` reports asset availability, not whether Gemma planned anything

**Severity:** nit
**File:** `internal/orchestrator/orchestrator.go:84-86`

### PR Comment

Line 85 sets `report.GemmaUsed = brain.NewLlamaCLIBackend(runner, opts.Home).Available(ctx).BrainPackAvailable`, but `BrainPackAvailable` is just a static asset-availability check (model file exists, sha256 OK, runtime executable) — Gemma is never actually invoked. The orchestrator's `supervise()` function at `orchestrator.go:162` is purely rule-based: it switches on `target` and `tun.RecommendedRepair` to return hardcoded `RescuePlanDecision` values, with no call to any brain backend. The result is that `gemmaUsed=true` will be emitted in `incident.json`, `agent-dispatch.md`, and the orchestrator JSON returned to GUI/OpenCode/support-bundle consumers on any machine that merely has the Brain pack installed, regardless of whether Gemma actually contributed to the plan.

### The mislabel

`report.GemmaUsed` (`schema.go:17`, JSON tag `gemmaUsed`) is documented and named to indicate that Gemma was used to plan the rescue. But `orchestrator.go:85` assigns it from `brain.NewLlamaCLIBackend(runner, opts.Home).Available(ctx).BrainPackAvailable`. `BrainPackAvailable` is defined in `internal/brain/llama_cli.go:73` as `out.ModelExists && out.ModelSHA256OK && out.RuntimeExecutable` — purely a check for whether the GGUF file and llama-cli binary exist on disk. It says nothing about whether the model was loaded or invoked.

### Why `supervise()` never actually uses Gemma

The supervisor at `orchestrator.go:162-183` is a closed switch on `target` and `tun.RecommendedRepair`. It returns one of three hardcoded `RescuePlanDecision` literals (the TUN repair plan, the OK "report" plan, or the manual_action plan). There is no `Generate(`, no `Planner.Plan(`, no `brain.RunLoop(`, no `llama-cli` invocation anywhere in `Run()`. The only brain reference in the entire orchestrator package is the `Available(ctx)` call on line 85 — a static disk check.

### Step-by-step proof of the misreport

1. User runs `agentlink orchestrator rescue --target clash-tun --json` on a Mac with the Brain pack installed (the Gemma GGUF and llama-cli are on disk).
2. `Run()` collects facts and calls `supervise(diag, tun, "clash-tun")`. Because `tun.RecommendedRepair == "tun"`, supervise returns the static `macos-clash-tun-force-repair` decision literal — no model loaded, no inference performed.
3. Line 85 then evaluates `brain.NewLlamaCLIBackend(...).Available(ctx).BrainPackAvailable`. Because the assets are present, this returns `true`.
4. `report.GemmaUsed = true` is set even though step 2 produced the plan deterministically with no model involvement.
5. `finish()` writes `incident.json` and `agent-dispatch.md` containing `"gemmaUsed": true`. The orchestrator JSON returned to the GUI/OpenCode/support bundle consumers carries the same field. The `Cycle` on line 87 also tags the validation step with `State="GemmaSupervise"`, reinforcing the false provenance.

### Contrast with the correct pattern

`internal/guided/guided.go:267` sets `PlannerUsed = true` only after the guided runner actually invokes `Planner.Plan(...)`. That is the right shape for a 'used' boolean.

### Impact

This is auditability/labelling, not data loss or a functional defect. The redacted support bundle and `agent-dispatch.md` are explicitly meant for human or Codex/OpenCode review, and the README markets this as "Gemma Rescue Supervisor". A reader of the bundle will be misled into believing a model consulted on the plan when in reality the plan came from a hardcoded rule table. (Note: `Models.swift`'s `GuidedRescueReport` only exposes `plannerUsed`, not `gemmaUsed`, so the Swift GUI's user-facing surface is currently unaffected; this bug primarily corrupts the JSON audit trail.)

### Fix

Three valid options:

1. Hardcode `report.GemmaUsed = false` here since `supervise()` never calls a backend.
2. Rename the JSON field to `gemmaPackAvailable` (and the Go field to `GemmaPackAvailable`) so the value matches its semantics.
3. Actually delegate plan selection to `brain.Planner` / `brain.RunLoop` and set `GemmaUsed=true` only after a successful `Generate` call, mirroring `guided.go:267`.
